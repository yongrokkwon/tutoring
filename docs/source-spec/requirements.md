# 광운대 공지사항 크롤러 — 요구사항 정의서

**버전**: v1.2
**최종 갱신**: 2026-05-13
**문서 성격**: "무엇을, 왜" — 시스템이 충족해야 할 정책·범위·제약을 정의. "어떻게 동작하는가"는 기능 명세서에 분리되어 있음.

---

## 1. 프로젝트 개요

광운대학교 공지사항을 자동 수집하여 최종적으로 카카오 알림톡으로 사용자에게 전달하는 시스템. 비전공자 학습 경로의 일부로, 결과물뿐 아니라 학습 과정 자체도 산출물.

## 2. 사용자 범위

- **1단계 MVP**: 개발자 본인 1인 전용. 회원가입/로그인 없음.
- **최종 목표**: 불특정 다수 광운대생 대상 공개 서비스.
- **설계 원칙**: 1단계부터 멀티유저 대응 DB 스키마/모듈 구조로 작성. 반복 리팩터링 회피.

## 3. 크롤링 대상

### 3-1. 게시판
- **URL**: `https://www.kw.ac.kr/ko/life/notice.jsp?srCategoryId=&mode=list&searchKey=1&searchVal=`
- **범위**: 광운대 메인 공지 게시판 1곳, 목록 1페이지만 훑음.
- **범위 외**: 학과/단과대 공지.

### 3-2. 카테고리 (12개, 정규화 테이블로 저장)

| ID | 카테고리 |
|---|---|
| (빈값) | 전체 |
| 0 | 일반 |
| 1 | 학사 |
| 2 | 학생 |
| 3 | 봉사 |
| 4 | 등록/장학 |
| 5 | 입학 |
| 6 | 시설 |
| 7 | 병무 |
| 8 | 외부 |
| 9 | 국제교류 |
| 10 | 국제학생 |

### 3-3. 중복 판별 키
- URL의 `DUID` 파라미터(정수). URL 전체는 참조용으로만 저장.
- 예: `notice.jsp?BoardMode=view&DUID=52497&tpage=1&searchKey=1&searchVal=&srCategoryId=` — DUID만 변하고 나머지는 진입 컨텍스트.

## 4. 운영시간 및 주기

### 4-1. 운영시간
- 평일 10:00 ~ 17:00만 동작.
- 야간·주말 정지.
- 공휴일은 평일이면 정상 동작(공휴일 무시 정책).

### 4-2. 주기 정책
- 크롤링 주기 = 알림 발송 주기 (묶임).
- 웹페이지에서 변경 가능. 기본값 = 중빈도.

### 4-3. 4모드

| 모드 | 동작 |
|---|---|
| 고빈도 | 15분 간격, 10:00~17:00, 총 29회 |
| 중빈도 (기본) | 매시 정각, 10:00~17:00, 총 8회 |
| 저빈도 | 17:00 1회 |
| 기타 | 사용자 지정 시각 리스트 (인접 ≥5분, 운영시간 내) |

## 5. 수집 정보

목록 페이지 기준 다음 필드를 수집한다.

| 필드 | 타입 | 비고 |
|---|---|---|
| DUID | 정수 | 중복 판별 키, 전역 UNIQUE |
| 제목 | 문자열 | |
| 카테고리 ID + 이름 | 정수 + 문자열 | categories 테이블 정규화 |
| 작성자(부서) | 문자열 | |
| 작성일 | 날짜 | |
| 수정일 | 날짜 | 변경 시 "수정됨" 알림 트리거 |
| 고정 여부 (is_pinned) | boolean | 페이지 상단 "Notice" 표기 구분 |
| 첨부 유무 | boolean | 알림에 📎 표시 |
| "신규게시글" 마크 | boolean | 보조 지표 (저장만, 알림/조회 미사용) |
| 원문 URL | 문자열 | 참조용 |

본문·첨부파일 실체는 1단계 미수집. DB 스키마에 `content`, `attachments` 컬럼 자리를 NULL 허용으로 미리 마련.

## 6. 첫 실행 처리

- DB `notices`가 비어 있으면 첫 실행으로 간주.
- 1페이지 모든 공지 DUID를 "이미 본 것" 상태로 DB 저장.
- 작성일이 첫 실행 당일인 공지만 알림 발송.
- 수정일은 첫 실행에서 무시.

## 7. 신규 판별 기준 (전역)

- DUID 없음 → **신규 공지**
- DUID 있고 수정일 변경 → **수정 공지**
- DUID 있고 수정일 동일 → 무시

## 8. 알림 채널과 메시지

### 8-1. 채널
- **1단계 MVP**: Discord 웹훅만.
- **1.5단계**: 카카오 알림톡(솔라피) 추가.
- 채널은 인터페이스로 추상화하여 구현체 교체/추가가 쉽도록 설계.

### 8-2. 메시지 양식

```
🆕 새 공지 N건
  · [카테고리] 제목 📎 (작성일) — 링크

✏️ 수정된 공지 M건
  · [수정] [카테고리] 제목 📎 (작성일) — 링크

발송 시각: YYYY-MM-DD HH:MM
```

- `new`와 `modified` 중 한쪽만 있으면 해당 섹션만 포함.
- 📎는 첨부 있을 때만 표시.
- new=0 AND modified=0이면 미발송.

### 8-3. 발송 단위
- 한 사이클에서 발견된 새/수정 공지는 메시지 1건에 묶어 발송 (Discord 임베드 활용).

### 8-4. 알림 일시정지
- `user_settings.is_active` 토글로 제어.
- OFF일 때: 알림 발송만 멈춤. 크롤링은 계속 동작.
- OFF 기간 공지는 누락(ON 복귀 시 새 공지부터만 알림).

## 11. 기술 스택과 정책

### 11-1. 기술 스택
- 언어: Python 3.11+
- 크롤링: requests + BeautifulSoup4
- DB: 표준 라이브러리 sqlite3 시작, 필요 시 SQLAlchemy
- 웹: Flask + Jinja2
- 스케줄링: 1단계는 프로세스 상주 + 내부 while 루프 + time.sleep. 2단계는 GitHub Actions cron.
- 알림: 1단계 Discord 웹훅 → 1.5단계 솔라피 카카오 알림톡
- 배포: 로컬 → Ngrok → Render
- 환경: venv + requirements.txt

### 11-2. 크롤링 정책
- User-Agent에 의도와 연락처 명시
- 요청 간격 ≥ 1초
- 타임아웃 10초
- 재시도 3회, 매 재시도 사이 고정 2초
- 응답 인코딩 UTF-8 정규화

### 11-3. 코드 스타일
- PEP 8 준수
- 변수/함수 snake_case, 클래스 PascalCase
- 타입 힌트 권장 (강제 아님)
- 함수 한 가지 일만 수행
- import 순서: 표준 → 서드파티 → 프로젝트 내부
- 로그는 `print` 사용

## 12. DB 스키마 미결정 사항 — 모두 해소됨

| 항목 | 결정 |
|---|---|
| A. 신규 판별 전역 vs 사용자별 | **전역** (notices에 DUID 존재 여부) |
| B. 카테고리 단순 TEXT vs 정규화 | **정규화 테이블** (categories) |
| C. `user_settings.is_active` 포함 여부 | **포함** (알림 일시정지) |

## 13. DB 테이블 윤곽 (잠정)

| 테이블 | 용도 |
|---|---|
| `users` | 사용자 |
| `user_settings` | 사용자별 설정 (frequency_mode, is_active 등) |
| `user_custom_times` | "기타" 모드의 시각 리스트 (1NF 정규화) |
| `categories` | 카테고리 ID·이름 매핑 |
| `notices` | 수집된 공지 |
| `notifications` | 발송 이력 (status 컬럼 포함) |

총 6개 테이블 예상. 세부 컬럼 정의는 DB 스키마 단계에서.
