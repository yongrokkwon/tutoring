# 광운대 공지사항 크롤러 — 기능 명세서

**버전**: v1.0
**최종 갱신**: 2026-05-13
**문서 성격**: "어떻게 동작하는가" — 각 기능 영역의 입력·처리 흐름·출력·예외를 정의. "무엇을, 왜"는 요구사항 정의서에 분리되어 있음.

---

## 기능 영역 구분

기능 영역 중심으로 4영역으로 나눈다.

| 영역 | 무엇을 하는가 |
|---|---|
| 1. 공지 수집 | 광운대 게시판 크롤링 + 스케줄링 + 신규 판별 + DB 저장 |
| 2. 알림 발송 | Discord 웹훅으로 신규/수정 공지 묶음 발송 |
| 3. 공지 조회 | 웹페이지에서 수집된 공지 목록 조회 |
| 4. 설정 관리 | 웹페이지에서 크롤링/알림 주기 변경 |

> 스케줄링은 별도 영역이 아니라 공지 수집의 한 부분으로 본다.

---

## 영역 1. 공지 수집

### [입력 — 트리거]

- **실행 방식**: 파이썬 프로세스 상주 + 내부 스케줄링
- **스케줄링 구현**: 단순 while 루프 + `time.sleep`
  - 주기적으로 깨어나 "지금이 발동 시각인가" 판단
  - 매 루프 1분마다 DB `user_settings` 재조회로 설정 변경 즉시 반영
  - 발동 시각 결정 = `user_settings.frequency_mode` 참조
- **운영시간 체크**: 함수 진입 시 가장 먼저 수행
  - 운영시간(평일 10:00~17:00) 외면 즉시 종료
  - 공휴일은 평일이면 정상 크롤링

### [처리 흐름]

**0. user_settings 재조회 (1단계 진입 이전)**

- `frequency_mode` 변경 시 발동 시각 계산 재산정
- `is_active` 값 캐시

**1. 운영시간 체크**

- 운영시간 외 → 즉시 종료 (아무 일도 안 함)

**2. HTTP 요청 — 게시판 목록 페이지**

- URL: `https://www.kw.ac.kr/ko/life/notice.jsp?srCategoryId=&mode=list&searchKey=1&searchVal=`
- User-Agent에 의도와 연락처 명시
- 타임아웃 10초
- 재시도 3회, 매 재시도 사이 고정 2초
- 재시도 대상: 모든 에러
- 3회 모두 실패 시: `print` 로그만 남기고 사이클 종료
- 응답 인코딩 UTF-8 정규화

**3. HTML 파싱 — 목록 1페이지의 각 행 추출**

수집 필드:
- DUID (URL 파라미터, 정수)
- 제목
- 카테고리 ID(정수) + 카테고리명(문자열)
- 작성자(부서)
- 작성일
- 수정일
- 고정 여부 (`is_pinned`, 행의 번호 자리가 "Notice"인지)
- 첨부 유무 (`Attachment` 표시 존재 여부)
- "신규게시글" 마크 여부
- 원문 URL

구체 셀렉터/파싱 규칙은 구현 단계에서 확정.

**4. 신규 판별 — 전역 기준**

파싱된 각 공지에 대해 DB `notices`에서 동일 DUID 조회:

| DB 상태 | 분류 |
|---|---|
| DUID 없음 | **신규 공지** |
| DUID 있고 수정일 변경됨 | **수정 공지** |
| DUID 있고 수정일 동일 | 무시 |

**첫 실행 분기** (DB `notices` 비어 있을 때):
- 파싱한 모든 공지를 DB에 저장 (이미 본 상태)
- 그중 작성일이 오늘 날짜인 공지만 "신규 공지"로 분류
- 수정일은 첫 실행에서 무시

**5. DB 저장**

- 신규 공지: `notices`에 INSERT
- 수정 공지: `notices`의 해당 행 UPDATE (수정일·제목 등 변경분 갱신)
- 무시 공지: DB 미변경

**6. 알림 영역으로 결과 전달**

- `user_settings.is_active == false` → 알림 영역 호출 생략
- `new`와 `modified` 둘 다 비어 있으면 → 알림 영역 호출 생략
- 그 외: 결과 객체 `{"new": [...], "modified": [...]}` 영역 2에 전달

### [출력]

- 알림 영역에 전달되는 결과 객체: `{"new": [...], "modified": [...]}`
- DB 상태 변경: `notices` 테이블에 INSERT/UPDATE 반영

### [예외 상황]

- **네트워크 오류 / 재시도 3회 실패**: 처리 흐름 2단계에 정의됨
  - 사이클 조용히 종료, `print` 로그만 기록
- **그 외 예외** (파싱 실패, DB 쓰기 실패, 필수 필드 누락 등):
  - 1단계 명세 범위 외
  - `try/except`로 잡고 `print` 로그만 출력, 다음 사이클로 진행
  - 실제 발생 시 그 시점에 정책 결정
- **사용자 설정 조회 실패**: 직전 캐시된 값 사용 (첫 조회부터 실패 시 기본값 적용)

## 영역 2. 알림 발송

### [입력]

- 영역 1이 전달한 결과 객체: `{"new": [...], "modified": [...]}`
  - 둘 다 비어 있으면 영역 2가 호출되지 않음
  - `is_active == false`면 영역 2가 호출되지 않음 (영역 1에서 차단)
- 사용자 정보: `users` 테이블의 `discord_webhook_url` 조회
  - 1단계는 사용자 1명, 1행만 읽음

### [처리 흐름]

**1. 메시지 본문 조립 (Discord 임베드 형식)**

```
🆕 새 공지 N건
  · [카테고리] 제목 📎 (작성일) — 링크

✏️ 수정된 공지 M건
  · [수정] [카테고리] 제목 📎 (수정일) — 링크

발송 시각: YYYY-MM-DD HH:MM
```

- `new` 또는 `modified` 중 한쪽만 있으면 해당 섹션만 포함
- 📎는 첨부 있을 때만 표시

**2. Discord 웹훅 POST 요청**

- 타임아웃 10초
- 재시도 3회, 매 재시도 사이 고정 2초

**3. `notifications` 테이블에 발송 이력 INSERT**

- 공지별 1행 (한 사이클 N건 묶음 발송이어도 N행)
- 컬럼: `user_id`, `notice_id`, `sent_at`, `channel`(=discord), `type`(=new|modified), `status`(=success|failed)
- 발송 성공 시 `status=success`
- 발송 3회 실패 시 `status=failed`로 기록 + `print` 로그

> **⚠ 현재 정책상 발송 실패한 공지는 자동 재시도되지 않음 — 누락 가능.** TODO로 개선 예정.

### [출력]

- Discord 채널에 메시지 1건 (성공 시)
- DB `notifications` 테이블에 발송 이력 INSERT (성공/실패 모두)

### [예외 상황]

- **Discord 웹훅 요청 실패**: 처리 흐름 2단계에 정의됨 (3회 재시도, 실패 시 status=failed로 기록)
- **메시지 길이 초과** (Discord 임베드 한계 도달): 1단계 명세 범위 외

## 영역 3. 공지 조회

### [화면 범위 — MVP]

### [라우팅]

| GET | `/notices` | 공지 목록 페이지 |
| GET | `/settings` | 주기 설정 페이지 (영역 4) |

| 메서드 | 경로 | 용도 |

### [네비게이션]

- 모든 페이지 상단에 메뉴바
- 메뉴 항목: 공지 / 설정
- 추후 메뉴 항목 추가 시 자리 마련 (이력 등)

### [/notices 페이지 — 공지 목록]

#### [입력]
- HTTP GET `/notices`

#### [처리 흐름]
1. DB `notices` 테이블에서 최근 100건 조회
   - 정렬: 1차 `is_pinned` DESC, 2차 `MAX(posted_date, modified_date)` DESC, 3차 `updated_at` DESC, 4차 DUID DESC. `MAX` 는 SQLite 의 스칼라 함수 (2 인자, 집계 아님).
   - LIMIT 100
2. 카테고리 ID → 한글명 매핑 (JOIN)
3. Jinja2 템플릿에 데이터 전달
4. HTML 렌더링

#### [출력]

- HTML 페이지
- 표시 컬럼: 카테고리 | 제목 | 작성자(부서) | 작성일(/수정일) | 원문 링크

**수정일 표시 규칙**:
- 수정일 == 작성일 → `작성: YYYY-MM-DD`
- 수정일 != 작성일 → `작성: YYYY-MM-DD / 수정: YYYY-MM-DD`

**부가 마크**:
- 📌 고정 공지 (`is_pinned=true`)
- 📎 첨부 있음 (`has_attachment=true`)
- ✏️ 수정된 공지 (`modified_date > posted_date`)

#### [예외 상황]
- DB 조회 실패: 1단계 명세 범위 외
  - `try/except`로 잡고 `print` 로그
  - 사용자에게는 500 에러 페이지 (Flask 기본)

#### [UI 디자인]
- 최소한: Flask 기본 + 간단한 CSS
- HTML 테이블 형태

## 영역 4. 설정 관리

### [라우팅]

| 메서드 | 경로 | 용도 |
|---|---|---|
| GET | `/settings` | 설정 페이지 표시 |
| POST | `/settings` | 설정 값 저장 |
| GET | `/settings/times/add` | "기타" 모드 시각 추가 — 그리드 표시 |
| POST | `/settings/times/add` | 그리드에서 선택한 시각 추가 |
| POST | `/settings/times/delete` | 등록된 시각 삭제 |

### [설정 항목]

- `frequency_mode`: 4모드(high/medium/low/custom) 라디오 버튼
- `is_active`: 알림 ON/OFF 체크박스
- `custom_times`: "기타" 모드일 때만 표시. 등록된 시각 목록 + [+ 시각 추가] 버튼

---

### GET /settings — 설정 페이지 표시

#### [입력]
- HTTP GET `/settings`

#### [처리 흐름]
1. DB `user_settings`에서 현재 사용자(1단계는 1명)의 설정 조회
2. `frequency_mode == "custom"`이면 `user_custom_times`에서 시각 목록 조회
3. Jinja2 템플릿에 데이터 전달

#### [출력]

HTML 페이지:

```
주기 설정
( ) 고빈도 — 15분마다 (10:00~17:00)
(•) 중빈도 — 매시 정각 (기본값)
( ) 저빈도 — 17:00 1회
( ) 기타  — 사용자 지정 시각

[기타 모드 선택 시 영역]
  현재 등록된 시각:
   · 10:30  [삭제]
   · 13:00  [삭제]
   · 16:15  [삭제]
  [+ 시각 추가]

알림 상태
[v] 알림 활성화

[저장]
```

---

### POST /settings — 설정 값 저장

#### [입력]
- HTTP POST `/settings`
- 폼 데이터: `frequency_mode`, `is_active`

#### [처리 흐름]
1. 폼 데이터 수신
2. `frequency_mode` 유효성 검증 (high|medium|low|custom 중 하나)
3. DB `user_settings` UPDATE (`frequency_mode`, `is_active`)
4. `/settings`로 리다이렉트 (PRG 패턴)

#### [출력]
- HTTP 302 리다이렉트 → `/settings`
- DB `user_settings` 행 UPDATE

#### [예외 상황]
- `frequency_mode` 잘못된 값: 폼 다시 표시 + 에러 메시지
- DB UPDATE 실패: 1단계 명세 범위 외 (500 에러)

> **PRG 패턴** (Post-Redirect-Get): 폼 POST 후 GET 페이지로 리다이렉트하는 패턴. 사용자가 새로고침했을 때 폼이 재전송되는 것을 막아줌. Flask에서 `redirect(url_for('...'))`로 구현.

### GET /settings/times/add — 시각 추가 그리드 표시

#### [입력]
- HTTP GET `/settings/times/add`

#### [처리 흐름]
1. DB `user_custom_times`에서 현재 등록된 시각 목록 조회 (이미 등록된 시각 비활성화 표시용)
2. 10:00~17:00 사이 15분 단위 시각 목록 생성 (10:00, 10:15, ..., 17:00)
3. Jinja2 템플릿에 데이터 전달

#### [출력]

HTML 페이지:

```
시각 선택 (15분 단위)

  10:00  10:15  10:30  10:45
  11:00  11:15  11:30  11:45
  12:00  12:15  12:30  12:45
  13:00  13:15  13:30  13:45
  14:00  14:15  14:30  14:45
  15:00  15:15  15:30  15:45
  16:00  16:15  16:30  16:45
  17:00

  [선택한 시각을 추가]   [취소]
```

- 이미 등록된 시각은 비활성화/표시 차별화
- 키보드 입력 없음. 모든 입력이 클릭으로만.

---

### POST /settings/times/add — 시각 추가

#### [입력]
- HTTP POST `/settings/times/add`
- 폼 데이터: 선택된 시각(들)

#### [처리 흐름]
1. 폼 데이터 수신 (선택된 시각 1개 이상)
2. 각 시각에 대해 검증:
   - 운영시간 내 (10:00~17:00) — 그리드 자체가 운영시간만 제공하므로 자동 충족
   - 이미 등록된 시각들과 인접 5분 이상 간격 (15분 단위 그리드라 자동 충족; 그리드가 더 촘촘해질 때 대비한 잠재 규칙)
   - 이미 등록된 시각과 중복 아님 (UNIQUE 제약으로도 차단)
3. 검증 통과 시 `user_custom_times` INSERT
4. `/settings`로 리다이렉트

#### [출력]
- HTTP 302 리다이렉트 → `/settings`
- DB `user_custom_times` 행 INSERT

#### [예외 상황]
- 검증 실패: 그리드 페이지 다시 표시 + 에러 메시지
- INSERT 실패 (UNIQUE 위반 등): 그리드 페이지 다시 표시 + 에러 메시지

---

### POST /settings/times/delete — 시각 삭제

#### [입력]
- HTTP POST `/settings/times/delete`
- 폼 데이터: 삭제할 시각 또는 `user_custom_times.id`

#### [처리 흐름]
1. 폼 데이터 수신
2. DB `user_custom_times` DELETE
3. `/settings`로 리다이렉트

#### [출력]
- HTTP 302 리다이렉트 → `/settings`
- DB `user_custom_times` 행 DELETE

#### [예외 상황]
- 존재하지 않는 ID: 무시 (이미 삭제된 것으로 간주), `/settings`로 리다이렉트
